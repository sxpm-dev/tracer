# Trace how your code actually runs

sx-tracing records instrumented JavaScript calls, their relationships, timings,
and consumer-defined data. Capture a scenario, inspect it in a dashboard, and
compare what changed in the next execution.

This is a technical introduction to the approach: how it recovers context from
`Error.stack`, where that works, and how the recording becomes evidence for
debugging, optimization, and execution comparisons.

## The idea: recover the active call from the stack

An `await` separates execution into continuations. A simple synchronous stack of
active calls cannot, by itself, identify the owner of the resumed work.

The tracing runtime associates named async wrappers with recording slots. On a
supported async chain, it inspects `new Error().stack`, finds the wrapper marker,
and looks up the active slot. Nested instrumentation can then attach to its owner.

<div className="sx-mechanism" aria-label="Stack recovery: wrapper, await, stack inspection, recording slot">
  <div><strong>Instrumented call</strong><code>named wrapper → slot</code><p>Associate an operation with capture state.</p></div>
  <div><strong>Resume after await</strong><code>new Error().stack</code><p>Find a wrapper marker in the supported stack.</p></div>
  <div><strong>Recover ownership</strong><code>slot → parent call</code><p>Attach the event to the recorded operation.</p></div>
</div>

**No error is thrown to perform this lookup.** Application errors are a separate
case: they are captured and rethrown. The mechanism avoids patching `Promise` and
does not require Node's `AsyncLocalStorage`, but stack inspection has a cost and
recovery depends on the engine and async boundary.

Read [the mechanism and examples](/guide/how-tracing-works/), then
[context boundaries](/guide/context-boundaries/) for the cases that need care.

## From instrumentation to a recording

The application defines the operations worth observing. A recording supplies the
capture boundary; a dashboard supplies a view of the saved evidence.

```text
Application functions + markers + consumer data
                     ↓
         @sx/tracing captures the scenario
                     ↓
       @sx/recordings batches session updates
                     ↓
     @sx/dashboard stores and presents the data
```

Open the application with `?install-tracing` before its modules load. This example
records a calculation in memory; session APIs can deliver it to the dashboard.

```ts
import {
  trace, marker, startRecording, releaseRecording,
} from '@sx/tracing';

const total = trace((prices: number[]) => {
  marker('cart-size', { items: prices.length });
  return prices.reduce((sum, price) => sum + price, 0);
}, 'total', { namespace: 'checkout' });

startRecording({ mode: 'full', cpu: false });
try {
  total([12, 8, 5]);
} finally {
  const recording = releaseRecording();
  console.log(recording.traces);
}
```

[Make your first recording](/guide/getting-started/) covers installation, capture,
transport, and inspection. The package names are intended release names; until
publication, use the repository or locally packed archives described in the guide.

## What the evidence lets you ask

### Understand and optimize with AI

Give AI a recording, the matching source revision, and the scenario. Ask it to map
observed calls to code, explain repeated work, and propose a measurable change.
Record the same scenario again to verify the outcome.

```text
Instrument → Record → Match evidence to source → Optimize → Record again
                         ↑                                  │
                         └──────── Compare results ─────────┘
```

A captured execution supplies context that an AI's fresh run may not reproduce.
An AI-run application can explore new hypotheses. Combine them: neither a trace
nor an agent's explanation is a correctness proof. [The complete workflow](/guide/ai-runtime-workflow/)
includes prompts, handoff artifacts, and tradeoffs.

### Detect changed execution behind green E2E tests

Two runs can reach the same screen through different paths. Compare normalized
call structure separately from elapsed time to find extra calls, unexpected
fallbacks, and retries early in CI.

| Observation | E2E baseline | Candidate |
| --- | --- | --- |
| Confirmation visible | Pass | Pass |
| Product fetches | 0, warm cache | 2 |
| Interpretation | Approved execution | Investigate the fallback and duplicate call |

This example is illustrative. Structural comparison and anomaly detection are
consumer-owned policies built on recording data, not automatic library features.
See [E2E comparisons and anomaly detection](/guide/execution-anomalies/) for
normalization, baseline management, and capture-quality checks.

## Extend the data and its presentation

Attach namespaced metadata to a ray, emit markers within a call, or register
collectors for recording-wide samples. Cache hits, queue depth, and domain outcomes
can sit alongside the generic call data.

The npm dashboard runs with a basic UI by default. Consumers can add columns,
blocks, pages, and data projections for their own signals.

- [Extra data per tracing ray](/guide/ray-metadata/): independent owners and async handles.
- [Cache telemetry example](/guide/cache-extension/): capture through to a custom view.
- [Dashboard extensions](/guide/dashboard-recipes/): reusable UI integration recipes.

For microfrontends, compatible package copies in one JavaScript realm share runtime
and transport ownership through `globalThis`. The shell owns capture; subsystems
contribute namespaced events. Separate iframes, workers, and backend services need
explicit correlation. [Shared-runtime integration](/guide/shared-runtime/).

## Packages and boundaries

| Package | Responsibility |
| --- | --- |
| [@sx/tracing](/guide/tracing/) | Instrumentation, markers, context recovery, and in-memory capture |
| [@sx/recordings](/guide/recordings/) | Recording sessions and batched transport; re-exports tracing APIs |
| [@sx/dashboard](/guide/dashboard/) | Installable UI, CLI, local server, data APIs, and extension points |
| [@sx/runtime-context](/runtime-context/) | Independent ambient context library |
| [@sx/tracer](/tracer/) | Original independent scope-based tracer with a different API |

These packages are not a distributed tracing platform. Captured behavior is only
as complete as the instrumentation and supported context boundaries. The library
does not automatically upload evidence to AI or resolve every event to source code.

## Performance is a measured tradeoff

Stack recovery and AsyncLocalStorage use different mechanisms with different
propagation coverage and costs. A faster microbenchmark does not establish lower
end-to-end application overhead. Compare the actual operation, engine, settings,
and workload before choosing a capture policy.

Read the [ALS comparison](/guide/async-local-storage/) for the idea, safety, and gaps;
the [Node 22/24 benchmark tables](/guide/context-benchmarks/) for measured numbers
and reproduction commands; and [performance evidence](/guide/performance/) for
what the current tests and measurements do—and do not—establish.
