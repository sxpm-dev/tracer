# Context access benchmark — 2026-11-11

[ALS comparison](../async-local-storage.md) · [Performance guide](../performance.md)

These are measured results for **`@sx/runtime-context` versus Node AsyncLocalStorage**,
not an ALS implementation of the full tracing/recording pipeline. Lower latency
is better. Each cell is the range of **task mean latencies from two separate process
runs**, not a confidence interval or per-operation minimum/maximum.

## Environment and method

- Source revision: `497a9c1` (runtime and benchmark source unchanged by this docs work).
- Apple M2 Max, arm64, macOS 15.7.3 (24G419).
- Node 22.16.0 / V8 12.4.254.21-node.26; Node 24.11.1 / V8 13.6.233.10-node.28.
- Tinybench 6.0.1; checked-in [benchmark source](../../packages/runtime-context/bench/context.bench.mjs).
- Each task: 1,000 ms measurement target, 250 ms warm-up, warm-up enabled.
- Two runs per Node version, run sequentially in separate Node processes.
- Developer desktop, no CPU isolation or fixed power/load controls. Documentation
  work and some example verification occurred during the measurement window.
  Treat these as local measurements, not release-grade controlled laboratory results.
- Same built context package for both runtimes, rebuilt before measurement.

## How to read the numbers

- **100 reads is one iteration**, not one read. Node 22's first run measured
  468 ns for the whole context task and 841 ns for ALS. Dividing by 100 gives
  4.68 and 8.41 ns as amortized task cost per read, including scope overhead;
  it does not isolate the cost of `get()` alone.
- **A ratio above 1 favors context**. `841 / 468 = 1.80`: ALS took about 1.80×
  the task latency in that particular run. It does not mean 80% less application
  latency, nor that the entire tracer is 1.80× faster.
- **The async row reverses the result**. Node 22's first run was 24,398 ns
  (24.398 μs) for context versus 1,254 ns (1.254 μs) for ALS: context took 19.46×
  as long. Node 24's first run was 24,101 / 611 = 39.45×. The table's inverse
  ratio is small and rounds to roughly 0.05 or 0.03.
- **Capture-local changes the workload**. Read once synchronously and reuse the
  local after awaits. It avoids repeated stack lookups: 1,585 ns versus 1,158 ns
  on Node 22's first run, and 421 ns versus 581 ns on Node 24's. That is a real
  optimization for suitable callers, not evidence that arbitrary async context
  access has become cheap.
- **The global is only a timing control**. One mutable global is not safe context
  propagation for concurrent operations. Never choose it because its row is faster.
- Raw `ops/sec` values and reciprocal mean latency need not coincide: the runner
  reports separately averaged statistics. Ratios above use the printed latency
  means, not its throughput column.

## Why these workloads behave differently

Source inspection shows the synchronous context path walking in-memory frames,
without stack reads. After awaits, the context implementation captures/formats
and parses stack information to recover a slot. ALS propagates execution context
instead. Reading once locally avoids repeated recovery. These explanations follow
the code; this run did not collect profiler evidence attributing every nanosecond.

ALS's results differ significantly between Node versions in this suite. Neither
“ALS is always slow” nor “one engine update makes every workload faster” follows.
The [concept comparison](../async-local-storage.md) covers propagation and safety.

## Limits of this experiment

Tasks execute in a fixed order in the same process for each run. ALS instances
are reused; runtime state and JIT history can affect subsequent tasks. There are
no concurrent requests, external I/O, actual timers in the timed async tasks,
browser workloads, allocation profiles, p95/p99 request latency, server upload,
metadata serialization, or dashboard measurements. `Promise.resolve()` supplies
the async boundaries. The script does not report confidence intervals or sample
counts in this output, and two process runs do not establish statistical significance.

Do not subtract the global row to manufacture a precise isolated API cost: its
scope semantics and generated code differ. Do not present synchronous savings as
proof of safe attribution. Use production-browser and application-level tests
before making deployment decisions.

## Reproduce

Use the exact source revision or record the new revision alongside your results.
From the repository root, select a Node version with your version manager:

```sh
yarn install
yarn workspace @sx/runtime-context build
node --version
node -p "process.versions.v8"
node packages/runtime-context/bench/context.bench.mjs
# Repeat in a fresh process, then repeat with the other Node version.
```

`yarn bench:context` also builds and runs this suite. Do not run suites in parallel
when comparing them. For publication-grade claims, repeat on an otherwise idle
machine, vary task order, retain sample-level statistics, and measure representative
concurrency and memory in addition to these microbenchmarks.
